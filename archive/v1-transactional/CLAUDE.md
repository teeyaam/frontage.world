# Frontage — orientation for a new Claude Code session

Read this first, before README.md or DEPLOYMENT.md. Those two files describe
the pre-launch demo build and are **now partly stale** (they still talk about
`data/db.json`, stubbed payments, Leaflet-only maps) — this file is the

staff permissions, contractor portal) that's still accurate; treat any
mention of "stubbed"/"JSON file"/"no API key needed for maps" there as

## What Frontage is

A physical-space advertising marketplace: sellers list wall/window/fence
space, buyers book it for a lease term, an independent contractor installs
the ad. Two separate identity spaces (buyer/seller accounts vs. contractor
accounts) share one Postgres database. Plain Node.js — no framework, no
build step (`http.createServer` + a manual router in `server.js`).

**Live at** `https://frontage.world`, hosted on Render, DNS on Cloudflare
(currently proxied — orange cloud — not DNS-only), domain bought via
Namecheap.

## Current architecture (all real, not stubbed)

| Concern | What's used | Where |
|---|---|---|
| Database | Postgres (Render-managed) | `lib/db.js` — every function is `async`, real SQL, no more JSON file |
| File uploads | Cloudflare R2 (S3-compatible) | `lib/upload.js`, falls back to local disk only if `S3_*` vars unset |
| Payments | Real Stripe — embedded Elements (no redirect), Connect Express for seller payouts | `lib/payments.js`, `routes/api.js` (`create-intent`, webhook) |
| Email | Resend | `lib/email.js` — verification emails, booking/job notifications |
| Maps | Google Maps JS API when `GOOGLE_MAPS_API_KEY` is set; Leaflet + OpenStreetMap (free, no key) otherwise | `public/google-map.js` / `public/map.js`, chosen at render time in `routes/pages.js#browsePage` |
| Geocoding | Free — small hardcoded table, then live Nominatim (OSM) lookup, then Sydney CBD fallback | `lib/geo.js` |
| Ads / monetization | Google AdSense, fully inert unless `ADSENSE_CLIENT_ID` is set | `lib/ads.js`, `/ads.txt` route in `server.js` |
| Site lock | Optional shared-passcode gate for pre-launch review, via `SITE_PASSCODE` env var | `server.js` (`handleGate`/`gatePage`) |

**The env-var-gated-feature pattern is deliberate and consistent**: every one
of the above (Stripe, S3, email, maps, ads, passcode) is fully inert with
zero footprint when its env var(s) are unset, and fully functional when set.
Don't break that invariant when adding new integrations — always give
yourself a working "unconfigured" fallback path, checked with an
`isXConfigured()` helper the way every existing lib does.

## Environment variables

`.env.example` documents every variable with no real values. The real `.env`
is local-only, gitignored, never committed — holds `DATABASE_URL`, R2/S3
creds, Stripe test keys, `SESSION_SECRET`, `RESEND_API_KEY`,
`GOOGLE_MAPS_API_KEY`, etc. The same values are set directly in Render's
dashboard for production (Render's env vars, not this repo, is what's
actually live).

**Known pitfall, already hit once**: if you ever paste a key from a masked
"Show key" field into Render's dashboard before actually clicking reveal,
you can end up with literal bullet characters (`•`) saved as the value
instead of the real key — the app runs fine, feature-detection sees the var
as "set," but every request using it fails silently downstream. If a
configured feature behaves like the key is wrong, the first move is
diffing the value actually saved in Render against the value you think you
copied — don't assume the Cloud/Stripe/etc. dashboard is misconfigured
before checking that.

## Deployment mechanics

- Push to `main` on GitHub → Render auto-deploys. I (Claude) can run
  `git push` directly — this repo's credential.helper is `manager` and
  credentials are already cached on this machine from prior manual pushes,
  so no browser login is needed for routine pushes.
- One-time scripts run directly against the live DB from a local shell with
  the real `.env` loaded: `scripts/run-schema.mjs` (applies
  `scripts/schema.sql`), `scripts/seed-db.mjs` (loads `data/seed.json`),
  `scripts/generate-demo-photos.mjs` (backfills demo listing photos — see
  below). None of these should be re-run against production without
  thinking it through first (seed/reset scripts are destructive).
- `scripts/schema.sql` is the schema source of truth — same snake_case
  columns / prefix-sequence id pattern (`L-1000+n`, `U-1000+n`, etc.) as the
  original JSON `data/seed.json` shape, so `lib/db.js`'s `rowToObj` mapping
  is mechanical.

## Demo content

The 10 seeded listings have illustrative SVG photos (venue scenes + an ad
mockup), generated by `scripts/generate-demo-photos.mjs` — **not real
photography**. This was a deliberate choice: these are fake demo businesses,
so real stock/venue photos would be both a copyright risk and misleading.
Keep that reasoning in mind if asked to add more demo listings later —
generate, don't source real images.

## Known environment quirks (this dev machine specifically)

- Windows + PowerShell primary shell; Bash tool also available (Git Bash,
  POSIX syntax) — pick the right syntax per tool, they don't share state.
- No `pandoc`/`soffice`/`pdftoppm` installed — the docx skill's normal
  visual-QA image-render step doesn't work here; fall back to `[xml]`
  well-formedness checks in PowerShell instead.
- This specific sandbox cannot reach some external hosts directly (Cloudflare
  R2's storage endpoint, and previously a pending Let's Encrypt cert on
  frontage.world) — TLS handshake fails locally even though the same
  request succeeds fine from Render's production servers. If a networked
  test fails only from this sandbox, that's the first thing to suspect
  before assuming a real production problem. `frontage.world` itself is
  also blocked from the Claude_Browser tool's navigate function by policy —
  test the live site by asking the user for screenshots/DevTools output, or
  by running the same code locally via `preview_start`/`.claude/launch.json`
  instead.
- The `Claude_Browser` preview tool runs on an embedded Electron/WebKit
  renderer, not a real user's Chrome/Safari/Firefox — it can behave
  differently from real browsers for things like WebGL-dependent rendering
  (observed once with Google Maps silently switching to a low-res static-image
  fallback with a hard ~800px width cap, purely a quirk of this test
  environment). Don't trust a rendering discrepancy found only in this tool
  as proof of a real production bug — corroborate with the user's actual
  browser (DevTools Console + Network tab) before concluding root cause.
